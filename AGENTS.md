# AGENTS.md

This file guides coding agents working in this repository. It records only what the code does not state plainly: package layout, scripts, routes and config are left to the tree.

## Monorepo

After creating a git worktree of this repo, run `bun install` inside it before running any workspace script — workspace module resolution is broken otherwise.

## Articles and the wiki importer

Each article carries a `tag` (article *kind* — Concept/Entity/Essay/Index, drives `/articles/tag/[tag]`), a `domain` (curated knowledge domain, drives `/articles/domain/[domain]`), and optional free-form `tags` (subject labels, drive `/articles/tagged/[tag]`). `@howardism/article-contract` is the source of truth for these, shared by the CLI (write side) and the blog (read side).

Most articles and the `data/*.json` manifests are generated by `bun run import:wiki` in `apps/cli` from an Obsidian-style vault (`WIKI_PATH`, optionally `RAW_PATH`). Ordering: `build:search-index` and `build:articles-meta` read the importer's output, so both must run *after* `import:wiki`. The blog reads the manifests at build time, so re-run the relevant command against the authoring root and publish a new release when source notes or articles change. For a full refresh (import + hero image generation + validation), use the `generate-wiki-images` skill in `.claude/skills/`.

Domains come from the vault's `_system/catalog.tsv`. The 14 `moc-*` pages and the 2 `generated: true` pages are the only pages allowed to have no catalog row; any other uncataloged page fails the import. The importer also refuses to run against a catalog older than the newest wiki file — regenerate it with `_system/build.py` in the vault.

### Content releases (R2)

Article content is not in Git. `apps/blog/src/content/` and the generated manifests in `apps/blog/src/data/` are gitignored and materialized by `bun run content:prepare` from the release pinned in `apps/blog/content.lock.json`: the public sample by default, the private full release when `CONTENT_PROFILE=full` (production only; needs R2 read keys). The root `build`/`lint`/`test`/`type-check` scripts prepare first. Author into an external `CONTENT_ROOT` (the importer, `build:*`, `translate` and `content:check` all honour it), never into `apps/blog/src`, which `prepare` overwrites. Publishing, cutover, rollback and GC are in `docs/r2-migration/README.md`.

`bun run content:check` is the content integrity gate and runs in CI.

### Hero images are WebP

`$imagegen` only emits PNG, and a 1600x900 lossless PNG of this flat-shaded art runs 1–8MB — the corpus reached 586MB before it was migrated. The importer transcodes each PNG to WebP and deletes the original. `bun run images:webp` does the same to any PNG it finds; it transcodes existing art rather than regenerating it, so it costs no image-generation quota. The `stray-pngs` warning in `content:check` is the tripwire for a PNG that escaped the transcode step.

The `-800`/`-1200` srcset variants are not referenced from the MDX: `render-article.tsx` imports them by slug with a template-literal `import()`, so a release without them still builds and the hero falls back to the 1600px original. The hero is a plain `<img>` from `getImageProps` with a hand-built `srcset`, because `next/image` drops `srcSet` when unoptimized. Its `sizes` is measured from the layout — overstating it sends 3x phones the 1600px file.

### Translation

The do-not-translate glossary (`apps/cli/src/glossary/`) is a per-machine, gitignored SQLite cache at `apps/cli/.translate-glossary.db`, seeded from the corpus on first use; a populated DB is left untouched so added terms persist. The `bun run glossary` CLI and the `glossary:mcp` server (registered in `.mcp.json`) share it.

`translate:check` runs in CI with `--warn`, posting annotations instead of failing the build. The translation engines (agy/codex) exhaust their quota mid-run, which is why `translate:drip` exists: it runs `translate --update` in small batches spaced across quota windows until `translate:check` reports nothing actionable.

## Lint config layout

`biome.json` (root), `apps/blog/biome.jsonc`, and `apps/cli/biome.jsonc` each extend the `ultracite/*` presets **directly**, so a rule set at the root does *not* reach the apps. Repo-wide deviations go in `biome.shared.jsonc`, which all three extend last (so it wins); each carries a comment saying why. `turbo.json`'s `lint` task lists every one of these files as an input — add new ones there or turbo serves a stale cached lint.

Two Biome behaviours worth knowing: a `// biome-ignore` comment must carry its whole reason on **one line** (a wrapped one silently stops suppressing), and the `noEqualsToNull` autofix is unsound — it rewrites `x == null` to `x === null`, dropping the `undefined` half. The rule is off for that reason.

## Bun-native file I/O

The CLI runs only under `bun`, so it reads with `Bun.file(path).text()` and writes with `Bun.write(path, data)` rather than `node:fs/promises`. `mkdir`/`readdir`/`rm`/`stat`/`rename` have no Bun equivalent and stay on `node:fs`. Two things do *not* move: `packages/article-contract`'s `createHash` (the blog imports that package and runs on Node, where `Bun` is undefined — and `sourceHash` is persisted in published releases), and `apps/blog/src`, for the same reason.

Undocumented, but verified: `Bun.write(path, data)` creates any missing parent directory, where `writeFile` raises `ENOENT`. So it is *not* a drop-in wherever that `ENOENT` is load-bearing — `import-wiki/emit.ts` relies on it to keep `main()` solely responsible for creating `articlesDir`, and has a test pinning that. `Bun.file(path).text()` *is* a drop-in for `readFile(path, "utf8")`: it throws with the same `code === "ENOENT"`.

## Deployment (Vercel, static export)

Vercel serves a **static export**, not a Next.js server build: `buildCommand` sets `DEPLOY_TARGET=vercel`, which builds `output: "export"` without trailing slashes, and `@vercel/next` deploys `out/` as plain files with no functions. Leave `framework` and `outputDirectory` out of `vercel.json`: `vercel build` treats `"framework": null` as unset rather than "Other", and `"outputDirectory": "out"` makes `@vercel/next` look for `out/routes-manifest.json` and fail. The reason is cost: a server build serves every prerendered page through ISR, and each regional-CDN miss bills an ISR read plus Fast Origin Transfer, which forced a move off Hobby in 2026-10. Images are unoptimized: Vercel's image optimizer caches a local-image variant for at most 31 days whatever `minimumCacheTTL` says, so every variant was re-transformed monthly, past Hobby's 5k cap, after which new variants return 402.

`vercel.json` is **generated**: edit `src/config/redirects.ts` or `security-headers.ts`, then run `bun run --cwd apps/cli vercel:config`; a CLI test fails when the committed file drifts. Vercel reads `vercel.json` before the build starts, so it cannot be generated during the build. It must sit in the Vercel project's Root Directory, `apps/blog`. Redirect and header `source` matching is case-sensitive, which is what makes the `/zh-tw/:path*` → `/zh-TW/:path*` rule safe. `bunVersion` accepts only `"1.4.x"` or `"1.x"`, never an exact patch.

### GitHub Pages backup (static export)

`.github/workflows/pages.yml` deploys a noindex static export to GitHub Pages on every push to `main`, while `www.howardism.dev` (Vercel) stays canonical. `DEPLOY_TARGET` must stay in turbo's `globalEnv` — turbo's strict env mode drops any build variable not listed there. The Pages export ignores `headers`/`redirects`: the CSP becomes a `<meta>` (HSTS and `X-Frame-Options` are unavailable), and `pages:redirects` writes meta-refresh stubs for every rule in `src/config/redirects.ts` — so a new redirect with a `:param` needs its values listed in `apps/cli/src/pages-export/redirects.ts` (an unlisted one is skipped with a warning). The R2 keys come from the `github-pages` environment — secrets on `content-integration` don't reach it.

Static export forbids runtime request data, so every route must prerender: `dynamicParams` is `false` on the dynamic routes, and `/compare` resolves `?ids=` on the client by fetching each article's prerendered page. In `pages:verify`, a page with no CSP meta and robots exactly `noindex` is a not-found render (`src/app/not-found.tsx` sits outside `(blog)/layout.tsx`), not a CSP failure.

## Code Style

The pre-commit hook runs `typos` over the whole working tree, untracked files included, so a flagged word in an uncommitted note blocks every commit: reword it or allow it in `_typos.toml`.
