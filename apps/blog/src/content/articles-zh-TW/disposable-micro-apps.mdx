## 摘要

[Thariq Shihipar](/articles/thariq-shihipar) 對 [HTML plans](/articles/html-as-the-new-markdown) 常見質疑的回答是：HTML 不像 Markdown 那麼容易編輯，那麼當你想修改 HTML 成品裡複雜的表格，或埋在其中的一組規則時，該怎麼辦？你可以**請 Claude 打造一個暫時、用完即丟的使用者介面，也就是 micro-app，專門編輯計畫中的那一小部分。**與其手動編輯成品，或在聊天中反覆折騰，不如生成一個*最適合這次編輯的工具*，用完就好。

> 「這甚至算不上個人軟體。這比較像是子……像是在微型軟體之上再搭一層微型軟體。」

## 實際範例

Thariq 的 HTML 實作計畫裡有一組**決策規則**，用來把不同類型的 CSV 資料轉換成視覺化內容。他覺得這些規則「有點武斷」，想進一步調整——但用文字或原始 HTML 編輯都很繁瑣。他使用的提示詞是：

```
I want to create an edible HTML artifact to help me define the decision rules...
I don't like the ones we have right now. Make this a custom UI that helps me with
structure but gives me flexibility. Design the ideal interface for this problem.
```

（「edible」是「editable」的筆誤——模型也順利處理了這個無傷大雅的錯字。）Claude 回傳了一個專用網頁：包含輸入欄位、下拉式選單、加入／移除按鈕，以及一個**可將最後設定以 Markdown 格式複製到剪貼簿的按鈕。**Thariq 以結構化、視覺化的方式編輯規則，整理出正確結果，再將完善後的資料帶回主要工作流程。

## 讓做法奏效的兩個設計要點

- **「Design the ideal interface for this problem.」**由人指定*問題*，而非預先列出元件清單，再讓模型挑選介面——既設下限制，也保留彈性；這和 [HTML as the New Markdown](/articles/html-as-the-new-markdown) 裡的提示方式相同。
- **複製回 Markdown。**micro-app 是覆蓋在持久文字之上的短暫*編輯介面*。這彌補了 HTML 最嚴重的弱點（差異比對／版本管理）：真實來源以 Markdown 往返，而豐富的介面只在編輯期間存在。

## 為什麼現在這樣做合乎理性：豐沛心態

在稀缺經濟下，為了做出一個編輯決定而啟動一次性應用程式，簡直荒唐。但在 [Compute Allocator](/articles/compute-allocator) 的**豐沛心態**下，這樣做合乎理性：生成成本低到足以讓一次性工具成為改善自身流程的合理投資。「現在我們負擔得起生成這些一次性工具，讓自己的流程更有效率、更愉快。」這是單一任務尺度下的 [Printing Press Software Democratization](/articles/printing-press-software-democratization)——軟體便宜到幾乎不費成本就能製作，因此成了用過即丟的便利工具，而不必成為一個專案。

## 開放問題

- 一次性 micro-app 和工具氾濫的界線在哪裡？如果每次編輯都會衍生一個專屬介面，工作流程會不會因此支離破碎？
- 「複製回 Markdown」的往返流程，除了設定類資料（規則、表格）之外，能否擴展到更豐富的成品？

## 已解決問題

- 這些 micro-app 能否套用範本並重複使用，而不是每次重新生成？什麼時候這會違背「一次性」的定位，轉而成為[持久工具](/articles/living-design-system)？**已回答：**[HTML Artifact Lifecycle: Where Plan History Lives, and When Disposable Becomes Durable](/articles/html-artifact-lifecycle-versioning-and-reuse)——正確的重用單位是*生成器*，而非成品：反覆出現的 micro-app 模式可成為一項技能，每次都重新生成符合需求的全新應用程式；如此保留一次性工具因應單項任務的貼合度，也具備重用所帶來的一致性（系統化程度的實測變化——每週活躍使用者中，使用技能的比例從 5.4% 上升至 26.6%）。只有在反覆出現、同步壓力與受眾三項條件都成立時，成品本身才會轉為持久資產（`design_system.html` 的狀態）；此時它也會帶來維護成本、同步頻率，並占用成品氾濫的膨脹上限。失敗模式是沒有做出選擇的中間狀態——應用程式留著卻無人維護：既氾濫又腐朽，既沒有貼合度，也沒有一致性。原則只有二選一：重新生成，或持續維護；絕不要只是留著。
