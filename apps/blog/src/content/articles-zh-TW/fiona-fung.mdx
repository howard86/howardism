## 摘要

她在 [Anthropic](/articles/anthropic) **領導 [Claude Code](/articles/claude-code) 與 [Cowork](/articles/cowork) 的工程和產品工作**；過去曾在 Meta 和 Microsoft 建立並帶領團隊（她在 2000 年代初期參與 Visual Studio）。她於 2026 年 5 月發表的演講〈Running an AI-Native Engineering Org〉，是組織領導層面的補充，與 [Cat Wu](/articles/cat-wu) 的產品觀點及 [Boris Cherny](/articles/boris-cherny) 的個人貢獻者觀點相互呼應：她說明當代理程式編碼成為全組織的預設方式後，*團隊流程如何被重新改寫*。她一以貫之的核心觀點是：**「過去對你有用的做法，現在可能不再適用」**——逐一檢視每個流程是否仍能發揮原本作用，因為瓶頸已經轉移。

> 注意：Fiona Fung 和 [Cat Wu](/articles/cat-wu) 都被描述為領導 Claude Code + Cowork 的產品工作。她們是互補的資深領導者——Fung 著重於*工程組織*（主管兼任個人貢獻者、審查、招募、規範）；Wu 則是產品負責人（節奏、評估、與 Boris 協作將願景轉化為產品）。職稱範圍有所重疊，應視為共同負責，而非彼此矛盾。

## 改變的五件事

她的演講以五項組織轉變為主軸，這些轉變發生在編碼不再是瓶頸之後：

1. **瓶頸轉移了**——從工程產能轉向驗證、審查和維護（[驗證成為新的瓶頸](/articles/verification-as-the-new-bottleneck)）。
2. **規範重新改寫**——TDD 不再帶來額外負擔；重構不再需要爭取預算；設計文件也精簡了（[建置很便宜，爭論很昂貴](/articles/building-is-cheap-arguing-is-expensive)）。
3. **真實依據來源轉移了**——從文件轉為簽入儲存庫的程式碼與技能（[以程式碼作為真實依據](/articles/code-as-source-of-truth)）。
4. **組織架構扁平化**——每位 Claude Code 主管都從個人貢獻者做起（[主管兼任個人貢獻者](/articles/managers-as-ics)）。
5. **產品判斷力成為稀缺技能**——透過不懈的自家試用來培養（[自家試用作為產品紀律](/articles/dogfooding-as-product-discipline)）。

## 她倚重的歷史類比

她將這描述為並非第一次發生的瓶頸轉移：2000 年代初期在 Microsoft，*建置*才是瓶頸——只有一間伺服器機房、需要輪值待命數週、合併佇列一次只能處理「六個 PR」，還得找出是哪個 PR 弄壞了建置。雲端與持續建置消除了那個瓶頸。代理程式編碼是「同類型的另一場轉變」。這種自律永遠適用：**流程會「悄悄失效」，而人們不會主動刪除流程——它們只會越積越多**（她講述 SLA 層層堆疊的往事）。因此，團隊原則之一是「明確授權淘汰舊流程」。

## 團隊原則（「必做事項」）與由下而上的決定

她帶領團隊共同採行的推動原則是：**每位隊友都使用 Claude Code 和 Cowork**；**「能 Claudify 的都 Claudify」**（Claude 做得到的事，就應該交給 Claude 做）；以及**明確授權淘汰舊流程**。至於其他一切——Claude 如何參與分流、每日站會，以及哪些工作流程先 Claudify——都交由各個 pod 由下而上決定。取得平衡的方法是：共同認同文化，同時保留調整空間。
