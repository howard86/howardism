## 摘要

[Fiona Fung](/articles/fiona-fung) 在 [Claude Code](/articles/claude-code) 推動的「大膽」組織調整是：**每位經理人都先擔任個人貢獻者（IC）**，並持續直接負責產品的一部分。組織維持「敏捷，並盡可能扁平」。這項做法之所以現在可行，是因為代理式編碼**大幅降低了入職成本**；過去這種成本讓經理人重新投入程式碼庫變得令人望而生畏。如今，經理人可以重新投入創作工作時數，而不必經歷痛苦的適應期。

## 這項調整

Fung 加入 Claude Code 後，最先做的事之一就是與招募團隊合作，讓**每位經理人在承擔支援團隊成員的責任前，先從個人貢獻者做起**。理由是，這讓經理人有機會「捲起袖子、深入程式碼庫，了解在團隊中擔任工程師是什麼感受」，再負起支援團隊成員的責任。她將扁平化組織加上經理人擁有 IC 職責，視為自己優先推動且「效果非常好」的三件事之一。

## 為什麼是現在：入職不再令人望而生畏

Fung 職涯中曾在經理人與個人貢獻者角色間轉換（Meta、Microsoft、Anthropic），每次回到 IC 工作時，她總會「有一點猶豫」——「如果有一陣子沒做，可能會令人望而生畏。」代理式編碼消除了這種阻力：她加入 Claude 時的入職「體驗截然不同」，因為她可以請 Claude 帶她熟悉各個面向，而不必增加工程師的負擔（[Code as Source of Truth](/articles/code-as-source-of-truth)）。過去讓經理人**離開**程式碼庫的成本——熟悉工作所需的時間，以及開口求助的社交成本——大幅下降。

## 以身試用的理由

更深層的原因是以身試用（參見 [Dogfooding as Product Discipline](/articles/dogfooding-as-product-discipline)）：「在 Claude Code，我們用 Claude 打造 Claude，也用 Claude Code 打造 Claude Code」；因此，不在程式碼庫工作的經理人，無法親身體驗自己正在交付的產品。讓經理人也擔任 IC，是領導團隊持續「從骨子裡感受產品」的方式。這是在管理層落實以身試用規範的結構性做法。

## 與工程師和 PM 融合的關聯

這是 [Engineer PM Convergence](/articles/engineer-pm-convergence) 在管理層的體現：[Boris Cherny](/articles/boris-cherny) 指出，Claude Code 團隊的*每一位*成員都會寫程式（工程經理、PM、設計師、資料科學家、財務人員、使用者研究員）。讓經理人也擔任 IC，將「人人都寫程式」延伸到組織架構的更高層，也符合 Anthropic 採行的精簡、扁平 [AI Native Product Cadence](/articles/ai-native-product-cadence)。

## 尚待探討的問題

- Fung 自己提出的問題：「iOS 和 Android 團隊還需要分開嗎？」——如果工程師能透過 Claude 跨平台工作，傳統的平台分工組織或許也會消失。扁平化會走到什麼程度？
- 經理人兼任 IC 能否擴展到一定的組織規模之外？還是只有在 Claude Code 規模小、程式碼庫容易讓 Claude 理解時才行得通？
